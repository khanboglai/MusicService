# Музыкальный стримминговый сервис

Проект представляет собой микросервисную архитектуру музыкального сервиса с разделением функций на отдельные сервисы: авторизация, работа с артистами и слушателями, метаданные, потоковое воспроизведение, поиск и аналитика. Основная цель — изолировать бизнес-логику и обеспечить масштабируемость, независимую разработку и хранение разных типов данных.

## Общая архитектура

Проект построен по принципам микросервисной архитектуры:

- отдельные сервисы отвечают за конкретную предметную область;
- внешние запросы идут через gateway;
- внутреннее взаимодействие между сервисами организовано через gRPC;
- публичные HTTP-эндпоинты реализованы на FastAPI;
- данные хранятся в нескольких системах: Postgres, Redis, Elasticsearch, MinIO, ClickHouse;
- аналитическая часть собирает события через Kafka и Debezium.

Подобная структура позволяет разделить ответственность между сервисами и упростить развитие отдельных компонентов без сильной связанности между ними.

## Сервисы проекта

### 1. gateway

Это входная точка для клиентских запросов. По структуре папок сервис содержит:

- app/main.py — точка запуска приложения;
- app/api — маршруты и обработчики API;
- app/core — настройки приложения и логирование;
- app/grpc_clients — клиенты для внутреннего общения через gRPC;
- app/schemas — схемы данных;
- app/domain_exceptions — пользовательские ошибки и обработка исключений.

Главная роль gateway — маршрутизировать запросы к соответствующим сервисам и скрыть внутреннюю микросервисную архитектуру от клиента.

### 2. artist_service

Сервис отвечает за работу с артистами. В коде видно разделение на слои:

- src/api — HTTP-эндпоинты;
- src/core — конфигурация и логирование;
- src/database — подключение к БД и модели;
- src/repositories — слой доступа к данным;
- src/domain_exceptions — доменные исключения;
- src/value_objects — значимые объекты домена;
- src/migrations — миграции Alembic;
- src/grpc — gRPC-сервер и протоколы для внутренних вызовов.

Также в сервисе есть поиск в Elasticsearch через модуль search.py.

### 3. listener_service

Этот сервис посвящён профилям пользователей/слушателей, лайкам, взаимодействию и пользовательской активности. В проекте заметны следующие компоненты:

- database/models.py — ORM-модели;
- database/repository — репозитории для работы с данными;
- domain/entities / domain/values — сущности и доменные значения;
- grpcc — gRPC-сервер и сгенерированный код по .proto файлам;
- migrations — миграции для модели слушателя и связанной активности.

У сервиса есть логика работающая с PostgreSQL через async SQLAlchemy и gRPC-интерфейсом для внутренней коммуникации.

### 4. metadata_service

Сервис метаданных разделён на две части:

- reader — чтение данных об альбомах и треках;
- writer — запись метаданных;
- common — общий код, модели, репозитории, зависимости и search-интеграция с Elasticsearch.

Это типичный пример разделения на read/write part: один сервис читает информацию, другой её обновляет. Для связи между внутренними частями используются FastAPI и gRPC, а для поиска — Elasticsearch.

### 5. reg_auth

Сервис регистрации и авторизации отвечает за:

- регистрацию пользователей;
- логин и выдачу токенов;
- получение данных текущего пользователя;
- административные операции.

В папке src есть отдельные модули:

- api/register.py
- api/login.py
- api/me.py
- api/admin.py
- grpc — gRPC-контракт и сервер;
- db и migration — работа с базой данных;
- schemas, utils, certs — вспомогательные компоненты.

Используются SQLAlchemy + PostgreSQL, JWT и безопасные методы хеширования паролей.

### 6. streaming_service

Сервис потокового воспроизведения и передачи медиа. В структуре заметны:

- apps/grpc — gRPC сервер для стриминга аудиофайлов;
- apps/core — настройки и логирование;
- объектная работа с файлами через MinIO;
- асинхронная передача данных через gRPC.

Это подтверждает, что проект поддерживает не только работу с метаданными и пользователями, но и непосредственную доставку аудиофайлов.

### 7. analytic_data

Папка analytic_data отвечает за аналитику и визуализацию данных:

- ClickHouse для хранения агрегированной статистики;
- Grafana для визуализации данных;
- Kafka Connect / Debezium для CDC (Change Data Capture);
- плагины для Grafana и Debezium.

Здесь видно, что проект собирает данные о прослушиваниях, жанрах, артистах и треках, чтобы строить аналитические дашборды по активности пользователей.

## Методы и подходы в проекте

### 1. Микросервисный подход

Каждая функциональная область является отдельным сервисом, что даёт независимость в развитии и развёртывании частей системы.

### 2. Слойная архитектура

В большинстве сервисов выделяются слои:

- API
- зависимости / DI
- core / config
- database / repository
- domain / entities / value_objects
- exceptions
- grpc

Такой подход облегчает поддержку и позволяет разделять бизнес-логику, инфраструктуру и API-уровень.

### 3. Repository pattern

В сервисах используется паттерн репозитория: логика доступа к данным вынесена из маршрутов и обработчиков в отдельные классы и модули.

### 4. gRPC для внутренних сервисов

Внутренние вызовы между сервисами реализованы через gRPC, что позволяет быстро и эффективно обмениваться данными между микросервисами и использовать .proto-схемы для контрактов.

### 5. REST через FastAPI

Внешние HTTP API реализованы через FastAPI и Pydantic, что удобно для создания документации, валидации запросов и быстрой разработки API.

### 6. Асинхронность

Проект активно использует async/await, SQLAlchemy async engine, а также asyncio для запуска фоновых задач и gRPC-серверов.

### 7. Поиск и аналитика

- Elasticsearch используется для полнотекстового и индексного поиска;
- Kafka + Debezium позволяют собирать изменения из источников данных и переносить их в аналитический стек;
- ClickHouse + Grafana дают возможность строить dashboards с метриками и статистикой прослушивания.

## Хранение данных и потоки информации

Схематично взаимодействие можно описать так:

1. Клиент обращается к gateway.
2. Gateway направляет запрос в нужный сервис.
3. Бизнес-данные хранятся в PostgreSQL и, при необходимости, индексируются в Elasticsearch.
4. Медиафайлы хранятся в MinIO.
5. Пользовательская активность и события обрабатываются через Kafka и попадают в ClickHouse для анализа.
6. Grafana визуализирует результаты аналитики.

## Запуск проекта

Основной запуск инфраструктуры задан в корневом docker-compose.yml:

```bash
docker compose up -d
```

Для отдельных сервисов также есть локальные docker-compose файлы. Обычно после запуска платформенных контейнеров можно запускать соответствующие микросервисы через Python/uvicorn или Dockerfile.

## Итог

Этот проект — пример современной музыкальной платформы с микросервисной архитектурой, выполненной на Python. В нём сочетаются:

- FastAPI и gRPC для сервисного взаимодействия;
- PostgreSQL и Redis для хранения и кэширования;
- Elasticsearch для поиска;
- MinIO для медиафайлов;
- Kafka, Debezium, ClickHouse и Grafana для аналитики;
- Docker Compose для сборки локальной инфраструктуры.

Такой стек позволяет создать масштабируемую и гибкую платформу для музыкального сервиса с поддержкой поиска, аудиопотоков, пользовательского контента и аналитики.
